## Project goal

Build two integrated services for a personal bookmark manager/private read-later application:

- A signed-in person can save bookmarks and organize them into collections.
- The frontend drives an authenticated backend API.
- Application data is persisted in SQL through Prisma.
- Authentication uses the supplied Auth0 OIDC tenant and Authorization Code flow with PKCE.
- The central invariant is that one person cannot see, edit, or learn that another person's data exists.

The submission must also demonstrate how AI agents were directed, reviewed, corrected, and verified. AI use is required, but all submitted work must be understood and defensible by the candidate.

## Required application scope

### Backend

- Provide `/collections` and `/bookmarks` resources.
- Each resource supports get one, list, create, update (`PUT`), patch (`PATCH`), delete, and filtering.
- Provide `GET /collections/:id/bookmarks`.
- Provide `/me`, returning the current signed-in person.
- A bookmark may belong to one collection or be uncategorized; collections and bookmarks belong to a person.
- Persist data for every route in SQL using Prisma.
- Provide seed data for at least two distinct users.

The assignment suggests these fields as a starting point, but the final schema and any changes must be justified:

- Collection: `id`, `name`, `ownerId`, `createdAt`, `updatedAt`.
- Bookmark: `id`, `url`, `title`, optional `notes`, optional `collectionId`, `ownerId`, `createdAt`, `updatedAt`.

### Frontend

- `/collections`: list the signed-in person's collections, view one, create, and delete.
- `/bookmarks`: list the signed-in person's bookmarks, view details, create, delete, and filter by collection.
- Integrate these pages with the authenticated backend API.

Do not treat the optional Dockerfile, CI/CD pipeline, `/all` page, or full-text search as core requirements. Consider them only after the required scope is solid.

## Core privacy and security invariant

Everything is private to the person who created it. There is no public content, shared feed, or ability to browse other users' data. The system is broken if user A can see, change, delete, enumerate, or learn of the existence of user B's collections or bookmarks.

Apply these guardrails to every implementation:

- Derive the current person from the validated bearer credential. Never treat a client-supplied `ownerId` as authority.
- Scope every read and write, including get-one, list, filters, relation queries, updates, patches, and deletes, to the authenticated owner.
- When assigning a bookmark to a collection, verify that the target collection belongs to the same authenticated person.
- Ensure nested access through `GET /collections/:id/bookmarks` preserves the same ownership boundary.
- Avoid response behavior that reveals whether another person's resource exists.
- Use the two-user seed data to prove tenant isolation.
- Keep credentials out of source code, committed configuration, prompts, and transcripts. Use the supplied test account without copying its password into repository documentation or logs.

For every owner-scoped resource lookup, return the same `404 Not Found` when the resource does not exist and when it belongs to another owner. Use the same generic response body and do not disclose which condition occurred. Do not return `403 Forbidden` for ownership mismatches. Apply this rule to direct resource routes, updates, patches, deletes, nested collection routes, collection filters, and bookmark `collectionId` references.

## Authentication requirements

- Require OIDC authentication on every backend API route.
- Use Authorization Code flow with PKCE using `S256`. Do not use implicit flow.
- Use the assignment's Auth0 discovery endpoint, client ID, callback URL, logout URL, scopes (`openid profile email`), and available API audience.
- Before selecting the design, inspect the tenant discovery document and JWKS to verify supported flows, token characteristics, and signing algorithms. Do not assume them.
- Accept only an Auth0 access token requested for audience `https://bbl-candidate-test-api` as the API Bearer credential. Do not accept an ID token as API authorization. The rationale and trade-offs are recorded in `README.md` and `DECISIONS.md`.
- Use just-in-time local-user provisioning on every authenticated route. Identify the Auth0 account by the unique combination of verified issuer (`iss`) and subject (`sub`), create a local user with a Prisma-generated UUID when missing, and use that UUID as `ownerId`.
- Seeded users are test fixtures separate from the real Auth0 account. Email and name are optional profile data and must never be used as ownership identifiers.
- Accept Bearer access tokens only. Validate the signature through the tenant JWKS with an explicit `RS256` allowlist, exact issuer, API audience, required `exp`, required `iat`, optional `nbf`, non-empty `sub`, and the expected frontend client identifier.
- Apply 60 seconds of clock tolerance to time validation. Cache JWKS keys according to the endpoint's cache behavior and refresh once when an unknown `kid` is received.
- Accept the frontend client identifier from `azp` or `client_id` only after a real token confirms which access-token profile the tenant issues, and require its value to match the assignment client ID.
- Do not require custom API scopes because the assignment defines none. Reject every validation failure and every ID token with a generic `401 Unauthorized`. Never log raw tokens.

- `GET /me` returns `id`, nullable `email`, nullable `name`, `createdAt`, and `updatedAt` for the current local user.

## Privacy errors

- Query resources using both resource ID and authenticated `ownerId`; do not perform a second unscoped lookup to distinguish missing from other-owner resources.
- A missing resource and an existing resource owned by someone else return the identical `404 Not Found` status and generic body.
- Never return `403 Forbidden` or ownership-specific wording for an ownership mismatch.
- Apply the same response to inaccessible parent collections in `GET /collections/:id/bookmarks`, inaccessible `collectionId` filters, and nonexistent or other-owner `collectionId` values supplied for bookmarks.
- An owned collection with no bookmarks returns a successful empty list; that result is distinct from an inaccessible collection.
- The shared error envelope is defined below and must not vary based on cross-owner existence.

## Response status and envelopes

- Every successful response has JSON fields `statusCode`, `message`, and `data`. The body `statusCode` must be derived from and equal the actual HTTP status.
- Successful reads, PUT, PATCH, and deletes use `200 OK`. Creates use `201 Created`.
- A successful single-resource operation places the resource object in `data`; a successful list places an array in `data`; a successful delete uses `data: null`.
- DELETE uses `200 OK`, not `204 No Content`, so it can return the consistent success envelope.
- Success messages are descriptive only and must never be used for frontend control flow.
- Every successful list response adds sibling `meta` fields `page`, `pageSize`, `total`, and `totalPages` alongside `data`.
- Errors have JSON fields `statusCode`, `code`, `message`, and `details`. `details` is always an array and must not echo rejected values, credentials, or internal exceptions.
- Request validation failures use `400 Bad Request`, code `VALIDATION_ERROR`, and message `Request validation failed`.
- Authentication failures use `401 Unauthorized`, code `UNAUTHORIZED`, message `Unauthorized`, and empty details.
- Missing and other-owner resources use the identical `404 Not Found`, code `NOT_FOUND`, message `Resource not found`, and empty details.
- Unexpected failures use `500 Internal Server Error`, code `INTERNAL_SERVER_ERROR`, message `Internal server error`, and empty details; do not expose implementation details.

## Resource schema and validation

- Reject unknown JSON properties and all client-supplied server-controlled fields, including `id`, `ownerId`, `createdAt`, and `updatedAt`.
- Validate route and relation identifiers as UUIDs. UUID values are generated by Prisma; clients never select identifiers or owners during creation.
- A collection has `id`, `name`, `ownerId`, `createdAt`, and `updatedAt`. Its writable field is `name`, which must be a trimmed, non-empty string of 1–100 characters. Duplicate collection names are allowed.
- A bookmark has `id`, `url`, `title`, nullable `notes`, nullable `collectionId`, `ownerId`, `createdAt`, and `updatedAt`.
- A bookmark `url` must be an absolute `http` or `https` URL no longer than 2,048 characters. Reject other schemes, including `javascript`, `data`, `file`, and `vbscript`.
- A bookmark `title` must be a trimmed, non-empty string of 1–300 characters. Duplicate bookmark URLs are allowed.
- Bookmark `notes` may be null and may contain at most 10,000 characters. Normalize an omitted, null, or blank notes value to null when the operation permits the field to be omitted.
- Bookmark `collectionId` may be null. A non-null value must be a UUID identifying a collection owned by the authenticated person.
- Mirror required scalar and relation guarantees with database constraints where PostgreSQL and Prisma support them.

## PUT and PATCH semantics

- `PUT` replaces the complete writable representation of an owned resource.
- Collection `PUT` requires `name`.
- Bookmark `PUT` requires `url` and `title`; omitted `notes` and `collectionId` become null.
- `PATCH` updates only fields present in the request and requires at least one writable field. Omitted fields remain unchanged.
- In bookmark `PATCH`, explicit null clears `notes` or `collectionId`. Collection `name` and bookmark `url` and `title` cannot be null.
- Collection `PATCH` currently requires `name` because it is the collection's only writable field, so its payload resembles collection `PUT` even though the operations have different semantics.
- Both methods apply the common validation and owner scoping. Neither method can modify `id`, `ownerId`, `createdAt`, or `updatedAt`.

## Filtering

- All filters run within the authenticated owner's scope; never filter a globally queried resource set.
- `GET /collections?name=<text>` performs a case-insensitive substring match against the authenticated owner's collection names. Trim the filter and require 1–100 characters.
- `GET /collections` without `name` returns a paginated list of the authenticated owner's collections.
- `GET /bookmarks?collectionId=<uuid>` returns bookmarks in one collection owned by the authenticated person. A malformed UUID returns the validation error; a missing or other-owner collection returns the uniform privacy-preserving 404.
- `GET /bookmarks?uncategorized=true` returns bookmarks whose `collectionId` is null. The only supported value when the parameter is present is the literal `true`; omit it to include both categorized and uncategorized bookmarks.
- `collectionId` and `uncategorized=true` are mutually exclusive and produce a validation error when combined.
- `GET /bookmarks` without either filter returns a paginated list of the authenticated owner's bookmarks.
- Do not add URL search, title search, full-text search, owner filters, or multiple collection IDs to the core filtering contract.

## Lists and pagination

- Apply offset pagination to `GET /collections`, `GET /bookmarks`, and `GET /collections/:id/bookmarks`.
- Accept integer query parameters `page` and `pageSize`. `page` defaults to 1 and must be at least 1. `pageSize` defaults to 20 and must be between 1 and 100 inclusive.
- Invalid, non-integer, or out-of-range pagination values return `400 VALIDATION_ERROR`.
- Apply authenticated-owner scoping and filters before counting or selecting a page.
- Order every list by `createdAt` descending and then `id` descending so pagination is deterministic.
- List responses contain `meta: { page, pageSize, total, totalPages }`, where `total` uses the same owner and filters and `totalPages` is `ceil(total / pageSize)` or 0 when `total` is 0.
- A page beyond the available results returns `200 OK` with an empty `data` array and metadata describing the requested page and actual totals.
- Add owner-first composite database indexes supporting the collection list, bookmark list, and bookmark-by-collection list order. Do not add full-text or trigram indexing to the core scope.

## Nested collection bookmarks

- Implement only the assignment-required nested read route: `GET /collections/:id/bookmarks?page=<page>&pageSize=<pageSize>`.
- Treat nesting as relational navigation; bookmarks remain independent SQL rows with nullable `collectionId` and are not embedded inside collection records.
- Validate the path `id` as a UUID, then resolve the parent by both collection ID and authenticated `ownerId` before listing bookmarks.
- A malformed parent ID returns `400 VALIDATION_ERROR`. A missing or other-owner parent returns the identical privacy-preserving 404. An owned collection with no bookmarks returns a paginated `200 OK` empty list.
- Query and count bookmarks using both the authenticated `ownerId` and parent `collectionId`, then apply the standard ordering and pagination contract.
- The nested route accepts only `page` and `pageSize`. Reject `collectionId`, `uncategorized`, collection-name filters, and other unsupported query parameters.
- For the same collection and pagination values, the nested route and `GET /bookmarks?collectionId=<id>` return equivalent bookmark data and metadata.
- Do not add nested create, PUT, PATCH, or delete routes. Bookmark mutations remain under `/bookmarks`.
- After a collection is deleted, its nested route returns 404 and its former bookmarks are retrieved as uncategorized bookmarks.

## Collection deletion

- Deleting a collection removes the collection but preserves every bookmark that belonged to it.
- Set each affected bookmark's `collectionId` to null so it becomes uncategorized; do not delete the bookmark.
- Apply the collection deletion and relation update atomically through the Prisma/PostgreSQL relation behavior.
- Scope the collection lookup and deletion to the authenticated owner. The operation must never alter bookmarks belonging to another owner.

## Test expectations

Automated tests are required as runnable evidence for the claims made about the application. Tests must go beyond happy paths and emphasize the privacy and authentication boundaries.

At minimum, the verification plan must cover:

- Authentication is required on every backend API route.
- The API access token is accepted only when it satisfies the documented validation rules; missing, malformed, expired, invalid, or otherwise unacceptable credentials and ID tokens are rejected with `401 Unauthorized`.
- Token tests cover signature failure, unsupported and `none` algorithms, unknown `kid`, wrong issuer, wrong audience, wrong frontend client, missing or invalid required claims, expiry, future `iat`, future `nbf`, JWKS refresh, ID-token rejection, and absence of raw tokens in logs.
- User A cannot read, list, filter, update, patch, delete, relate, or infer the existence of user B's collections or bookmarks.
- Privacy tests compare status and response body for missing and other-owner IDs across direct, nested, mutation, deletion, filter, and relation-validation paths; both must receive the same generic `404 Not Found` response.
- Response-contract tests prove that actual and body status codes match, success and error envelopes have the documented shape, deletes return `200` with `data: null`, and sensitive values or internal errors are never included.
- A bookmark cannot be attached to another user's collection.
- Filtering tests cover case-insensitive collection-name matching, owned collection IDs, uncategorized bookmarks, invalid and combined parameters, empty results, and strict owner isolation.
- Pagination tests cover defaults, bounds, invalid values, deterministic ordering and tie-breaking, filtered totals, out-of-range pages, nested lists, and owner-isolated counts.
- Nested-route tests cover malformed, missing, other-owner, empty, populated, paginated, deleted-parent, and unsupported-query cases plus equivalence with the bookmark `collectionId` filter.
- CRUD, filtering, `/me`, and `GET /collections/:id/bookmarks` follow the documented API contract and persist through Prisma/SQL.
- Deleting a collection preserves its bookmarks and atomically sets their `collectionId` to null, without changing another user's bookmarks.
- Tests preserve strict owner-only access because sharing is deferred for the current submission.
- The two required frontend pages work against the authenticated API for their assigned operations.
- The core flow works end to end: sign in with Authorization Code + PKCE, obtain the chosen token(s), call the authenticated API, and persist data.
- Initial-provisioning tests cover successful `/userinfo` enrichment and timeout/error responses that leave nullable profile fields empty while allowing the authenticated request to continue.
- Resource-validation tests cover unknown and server-controlled fields, malformed UUIDs, boundary lengths, blank required strings, disallowed URL schemes, nullable fields, duplicate names and URLs, and same-owner collection references.

Mocking part of authentication in tests is allowed only when it is disclosed and the application's real token-validation path is still exercised. Keep verification reproducible and document how to run it.

- Frontend automated tests use Vitest.
- Backend automated tests use Jest with Nest testing utilities (`@nestjs/testing`).
