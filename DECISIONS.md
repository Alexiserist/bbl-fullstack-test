# Decisions

## ADR-001: Use an access token as the API Bearer credential

- Status: Accepted
- Date: 2026-08-04

### Context

The assignment requires a decision between the tokens returned by the Auth0 Authorization Code with PKCE flow. An ID token communicates authentication information to the client application; its audience is the client. An access token requested for the custom API is intended to authorize calls to that API and can carry the API audience.

The live tenant discovery document advertises Authorization Code flow, PKCE with `S256`, and a JWKS endpoint. The assignment provides the custom API audience `https://bbl-candidate-test-api`.

### Decision

The backend will accept only an Auth0 access token requested for audience `https://bbl-candidate-test-api` in the HTTP `Authorization: Bearer <token>` header. It will not accept an ID token as API authorization.

Before authorizing a request, the backend validates the token using the policy in ADR-006. The tenant's current JWKS confirms `RS256`; a real audience-bound access token is still needed to confirm whether this tenant's client claim is `azp` or `client_id` for final environment configuration.

### Rationale

Accepting an audience-bound access token prevents the API from treating a token intended for the frontend client as API authorization. This reduces token-substitution and confused-deputy risk and follows Auth0's documented token purposes.

### Consequences and trade-offs

- The frontend must include the API audience when starting authorization; otherwise Auth0 may issue a token intended only for `/userinfo` rather than this backend.
- Profile claims such as email are not guaranteed to be in the API access token. Local-user mapping relies on verified issuer and subject as defined in ADR-004.
- Access tokens are bearer credentials: disclosure permits use until the token expires, so they must not be logged or committed.
- Current JWKS keys are marked `RS256`, but the backend must not hardcode a key identifier because signing keys can rotate.

### Evidence

- Tenant discovery: <https://dev-yg.us.auth0.com/.well-known/openid-configuration>
- Tenant JWKS: <https://dev-yg.us.auth0.com/.well-known/jwks.json>
- Auth0 token guidance: <https://auth0.com/docs/secure/tokens>
- Auth0 access-token validation guidance: <https://auth0.com/docs/secure/tokens/access-tokens/validate-access-tokens>

## ADR-002: Scope all API operations to the authenticated owner

- Status: Accepted
- Date: 2026-08-04

### Context

The assignment's central privacy invariant says one person must not see, edit, or learn of another person's data. A proposed future admin use case considered allowing `PATCH` to override `ownerId`, but the assignment defines no admin role, permission, ownership transfer, or audit behavior.

### Decision

Every backend route requires authentication, and every collection and bookmark operation is scoped to the authenticated owner. The server derives ownership from the validated Auth0 identity and local-user mapping.

`ownerId` is server-controlled, excluded from writable payloads, and immutable through `POST`, `PUT`, and `PATCH`. Requests that contain `ownerId` are rejected. The current API has no admin bypass or ownership-transfer operation.

### Rationale

Allowing an ordinary update payload to select an owner would create a direct cross-user data-access path and violate the assignment's privacy invariant. Keeping ownership outside writable resource fields makes the secure path the default for every route.

### Consequences and trade-offs

- Current users cannot transfer resources between owners.
- No administrator can access or reassign another person's data through this API.
- A future administrative capability would require an explicit product requirement, separate authorization policy, API contract, and verification. It cannot be added by enabling `ownerId` in the existing patch schema.
- Auth0 identity maps to a local user through the verified issuer and subject as defined in ADR-004.

## ADR-003: Use PostgreSQL with Prisma and UUID identifiers

- Status: Accepted
- Date: 2026-08-05

### Context

The assignment requires SQL persistence through Prisma but does not prescribe a database engine or identifier type. PostgreSQL, MySQL, and SQLite were considered. The project also needs relational ownership constraints, a nullable collection-to-bookmark relation, reproducible local setup, and potential room for the optional full-text-search bonus.

### Decision

Use PostgreSQL 18.4 as the database, accessed only through Prisma ORM. Run PostgreSQL locally through Docker Compose using the official `postgres:18.4` image. Use UUID identifiers generated by Prisma for application entities and their foreign-key references, stored using PostgreSQL's native UUID type.

Do not add TypeORM. Although PostgreSQL supports it, using a second ORM would add complexity and conflict with the assignment's explicit Prisma requirement.

### Rationale

PostgreSQL provides native UUID columns, strong foreign-key and referential-action support, and good support across Prisma migrations, filtering, indexing, and transactions. Docker Compose makes the local database reproducible without depending on an externally hosted service.

### Consequences and trade-offs

- Local development and tests require a running PostgreSQL service rather than a single SQLite file.
- Repository setup documentation must explain how to start and initialize the Compose database.
- Database configuration must come from `DATABASE_URL`; credentials must not be committed.
- PostgreSQL-specific migrations may make later migration to another database non-trivial.
- Inserts performed outside Prisma must supply their own UUID because the identifier default is applied by Prisma rather than by PostgreSQL.

## ADR-004: Provision local users just in time from verified OIDC identity

- Status: Accepted
- Date: 2026-08-05

### Context

Auth0 identifies an authenticated account using the token's issuer (`iss`) and subject (`sub`), while collections and bookmarks require a local UUID `ownerId`. The real Auth0 user's subject is not known before the first successful authentication, and the assignment separately requires seeded data for at least two users.

### Decision

Resolve or provision the local user on every authenticated route after validating the access token. Identify the Auth0 account with the unique combination of issuer and subject. If no matching local user exists, create one with a Prisma-generated UUID and use that UUID as the owner of collections and bookmarks.

Enforce a database uniqueness constraint on `(authIssuer, authSubject)` and use an atomic upsert or equivalent unique-constraint recovery for concurrent first requests.

Seeded users are deterministic test fixtures and are separate from the real Auth0-backed account. Email and name are optional profile attributes and never serve as identity or ownership keys.

### Rationale

Just-in-time provisioning avoids manually creating the real Auth0 user before its stable subject is known. Using the issuer and subject together follows OIDC identity semantics, while a separate local UUID keeps application ownership independent from the identity provider.

### Consequences and trade-offs

- A user's first valid request may write a local user record even when the requested route is not `/me`.
- Token validation must finish successfully before any user lookup or creation is trusted.
- Concurrent first requests require atomic handling to avoid duplicate local users.
- Email changes do not change ownership, and matching emails must not automatically merge accounts.
- The `/me` response and profile-enrichment policy are defined in ADR-005.

## ADR-005: Return a minimal local profile from `/me`

- Status: Accepted
- Date: 2026-08-05

### Context

The frontend needs to identify the signed-in account, but the API access token is an authorization credential and is not guaranteed to contain profile claims. The tenant supports `openid profile email`, and Auth0 exposes `/userinfo` as a trusted profile source. Email and name can be missing or change and therefore cannot be ownership identifiers.

### Decision

`GET /me` returns the local user's `id`, nullable `email`, nullable `name`, `createdAt`, and `updatedAt`. It does not return tokens, `authIssuer`, or `authSubject`.

During initial just-in-time provisioning of a newly created local user, the backend attempts one Auth0 `/userinfo` request using the validated access token and a short timeout. If it succeeds, available email and name values are stored locally. If it fails or the claims are absent, the fields remain null and the authenticated request continues. Existing users do not call `/userinfo` again; continuous synchronization is not implemented.

The frontend displays name when available, otherwise email, otherwise a generic signed-in label. Email and name never determine identity or ownership.

The API requires and validates `exp` on every access token. Expired tokens and tokens missing required validation claims are rejected with `401 Unauthorized`.

### Rationale

This gives the frontend useful account context without misusing the ID token as API authorization or coupling ownership to mutable profile data. Persisting profile values avoids calling Auth0 on every `/me` request.

### Consequences and trade-offs

- Stored profile values can become stale because continuous synchronization is not implemented.
- Missing profile claims produce null values and do not change the `(iss, sub)` identity mapping.
- Auth0 `/userinfo` timeout, network, rate-limit, or error responses do not prevent a validated user from accessing the application.
- The actual audience-bound token must be verified to work with `/userinfo` during end-to-end authentication testing.
- The exact short timeout duration remains `TODO`.
- The complete access-token validation policy is defined in ADR-006; only live confirmation of `RS256` and the client-claim name remains pending.

## ADR-006: Validate API access tokens against a strict Auth0 policy

- Status: Accepted, pending live-token confirmation
- Date: 2026-08-05

### Context

The API accepts Auth0 access tokens as Bearer credentials. Signature verification alone is insufficient: a correctly signed token can still be expired, intended for another API, requested by another client, or missing the end-user identity required for owner scoping. The live discovery document and JWKS advertise the necessary endpoints and current RSA keys, but a real audience-bound token has not yet been obtained.

### Decision

Accept access tokens only from the HTTP Bearer authorization scheme. Validate the signature through the tenant JWKS with an explicit `RS256` allowlist, exact issuer, API audience, required `exp`, required `iat`, optional `nbf`, non-empty `sub`, and the expected frontend client identifier.

Apply 60 seconds of clock tolerance. Cache JWKS keys according to the endpoint's cache behavior and refresh once for an unknown `kid`. Depending on the confirmed access-token profile, require either `azp` or `client_id` to equal the assignment client ID.

Do not require custom API scopes because the assignment defines none. Reject every validation failure and all ID tokens with a generic `401 Unauthorized`. Never log raw tokens.

Before authentication implementation begins, inspect a real access token requested for `https://bbl-candidate-test-api` to confirm that it uses `RS256` and whether its client claim is `azp` or `client_id`.

### Rationale

The policy binds the token to the expected issuer, backend API, frontend client, validity window, signing key, and end-user subject. An explicit algorithm allowlist prevents algorithm-confusion and unsigned-token acceptance, while JWKS refresh supports safe key rotation.

### Consequences and trade-offs

- Authentication implementation is blocked until the real-token profile confirms the two pending facts.
- A token issued for the API but requested by another Auth0 client is rejected.
- A 60-second tolerance accepts small clock differences while slightly extending the effective time boundary.
- Unknown signing keys cause one JWKS refresh and then a generic authentication failure.
- Adding endpoint permissions later would require a new documented scope policy; none is inferred now.

Other unresolved requirements remain marked `TODO` in `AGENTS.md`.

## ADR-007: Use a minimal resource schema with strict input validation

- Status: Accepted
- Date: 2026-08-05

### Context

The assignment supplies starting fields for collections and bookmarks but leaves their final schema and validation rules to the candidate. Validation must support normal bookmark management while preventing mass assignment of ownership and unsafe or unusable resource values. The assignment does not require collection-name uniqueness or bookmark-URL uniqueness.

### Decision

Keep the assignment's suggested resource fields without adding product fields. A collection contains `id`, `name`, `ownerId`, `createdAt`, and `updatedAt`; only `name` is writable. A bookmark contains `id`, `url`, `title`, nullable `notes`, nullable `collectionId`, `ownerId`, `createdAt`, and `updatedAt`; only `url`, `title`, `notes`, and `collectionId` are writable.

Reject unknown request properties and client-supplied `id`, `ownerId`, `createdAt`, or `updatedAt`. Validate identifiers as UUIDs. Collection names are trimmed and must contain 1–100 characters. Bookmark titles are trimmed and must contain 1–300 characters. Bookmark URLs must be absolute `http` or `https` URLs no longer than 2,048 characters. Notes are nullable with a 10,000-character limit, and blank notes normalize to null. `collectionId` is nullable; a non-null value must identify a collection owned by the authenticated person.

Allow duplicate collection names and duplicate bookmark URLs. Mirror required scalar and relation guarantees with database constraints where PostgreSQL and Prisma support them.

Required-versus-optional field presence for `PUT` and `PATCH` is defined in
ADR-010. Validation failures use the `400 VALIDATION_ERROR` envelope defined
in ADR-012; details may identify fields and constraints but never echo
rejected values.

### Rationale

The selected fields meet the required scope without inventing tagging, sharing, or other product concepts. Scheme restrictions prevent the application from storing dangerous executable or local-file URL schemes. Length limits bound storage and request abuse while remaining generous for normal bookmark data. Rejecting unknown and server-controlled fields makes ownership and identifiers explicitly non-writable. Allowing duplicates avoids inventing uniqueness behavior that the assignment does not request.

### Consequences and trade-offs

- Users may create collections with the same name and save the same URL more than once.
- Only `http` and `https` bookmarks are supported; other URI schemes are rejected.
- Whitespace-only notes are not distinguishable from no notes.
- Every non-null bookmark-to-collection assignment requires a same-owner lookup, including create, PUT, and PATCH.
- Automated tests must exercise boundary lengths, malformed UUIDs, disallowed URL schemes, unknown fields, server-controlled fields, nullable values, duplicates, and cross-owner collection references.

## ADR-008: Preserve bookmarks when their collection is deleted

- Status: Accepted
- Date: 2026-08-05

### Context

The assignment allows a bookmark to belong to one collection or to be uncategorized, but it does not define what happens to bookmarks when their collection is deleted. The considered behaviors were deleting the bookmarks, rejecting deletion of a non-empty collection, or preserving the bookmarks as uncategorized.

### Decision

Deleting a collection removes the collection and preserves all bookmarks that belonged to it. Each affected bookmark's `collectionId` becomes null. Implement this atomically through the Prisma relation and PostgreSQL foreign-key referential action.

The collection lookup and delete remain scoped to the authenticated owner. Same-owner relation validation and constraints ensure the operation cannot modify another owner's bookmarks. Success responses follow ADR-012; missing and other-owner collections follow ADR-011 and the exact envelope in ADR-012.

### Rationale

The application already supports uncategorized bookmarks, so clearing the relation uses required behavior rather than introducing a new state. It also avoids unexpected bookmark data loss and does not force users to empty a collection before deleting it.

### Consequences and trade-offs

- Collection deletion is non-destructive to bookmark content.
- Bookmarks from the deleted collection appear as uncategorized afterward.
- Restoring the deleted collection does not automatically restore its former bookmark relationships.
- Persistence must make the collection removal and relation updates one atomic operation.
- Automated tests must verify the nulling behavior and prove that another owner's bookmarks remain unchanged.

## ADR-009: Defer collection sharing

- Status: Accepted for the current submission
- Date: 2026-08-05

### Context

The assignment mentions a desire to share a collection but does not define recipients, permissions, invitation or revocation behavior, discovery, or how sharing interacts with the central rule that one person must not learn of another person's private data. Implementing a partial sharing model would require inventing security-sensitive product requirements.

### Decision

Do not implement collection sharing in the current submission. Do not add share records, invitations, public links, shared-resource routes, or authorization exceptions. Collections and bookmarks remain accessible only to their authenticated owner.

Sharing may be designed later as a separate feature. Its recipient identity, permissions, grant and revocation lifecycle, resource-discovery behavior, privacy responses, and tests remain `TODO` until that future work is explicitly started.

### Rationale

Deferral preserves the assignment's explicit privacy invariant and keeps the initial authorization model small enough to verify. It also makes the omission visible instead of silently inventing a sharing contract.

### Consequences and trade-offs

- The current submission does not satisfy the stated desire to share collections.
- No current route may grant one user access to another user's collection or bookmarks.
- Owner-isolation tests have no shared-access exception.
- Future sharing work requires a new authorization and API decision before implementation.

## ADR-010: Distinguish complete PUT replacement from partial PATCH updates

- Status: Accepted
- Date: 2026-08-05

### Context

The assignment requires both `PUT` and `PATCH` for collections and bookmarks but does not define how omitted fields behave. Without an explicit distinction, clients could accidentally retain values they expected to clear or clear values they expected to preserve.

### Decision

`PUT` replaces the complete writable representation. Collection `PUT` requires `name`. Bookmark `PUT` requires `url` and `title`; omitted `notes` and `collectionId` become null.

`PATCH` updates only supplied fields and requires at least one writable field. Omitted fields remain unchanged. Explicit null clears bookmark `notes` or `collectionId`; collection `name` and bookmark `url` and `title` cannot be null.

Collection `PATCH` currently requires `name` because it is the resource's only writable field. Its payload therefore resembles collection `PUT`, although its semantics remain partial rather than complete replacement.

Both methods reject unknown and server-controlled fields, validate any supplied values under ADR-007, scope the target lookup to the authenticated owner, and validate a non-null bookmark `collectionId` against a collection owned by that same person. Neither method provides an ownership or administrative override.

### Rationale

The distinction gives omitted fields predictable meaning and makes PATCH safe for focused edits. Treating omitted nullable bookmark fields as null under PUT produces an actual replacement rather than a partial update with a different method name.

### Consequences and trade-offs

- A bookmark client using `PUT` must send every value it wants to preserve.
- A bookmark client using `PATCH` can clear nullable values explicitly without resending unrelated fields.
- Collection PUT and PATCH have the same payload shape until the collection gains another writable field.
- Validation error statuses and response envelopes are defined in ADR-012.
- Tests must distinguish omission behavior for PUT and PATCH and cover empty patches, explicit null, ownership isolation, and server-controlled fields.

## ADR-011: Hide cross-owner resource existence with a uniform 404

- Status: Accepted
- Date: 2026-08-05

### Context

The central privacy invariant prohibits one person from learning whether another person's resource exists. Returning `403 Forbidden` for an existing other-owner resource but `404 Not Found` for a nonexistent resource would reveal that distinction. Performing an unscoped existence check would also create an unnecessary path around owner scoping.

### Decision

Query every private resource by both its identifier and the authenticated local `ownerId`. If no owned record is found, return the identical generic `404 Not Found` status and response body whether the identifier is globally absent or belongs to another owner. Do not perform a second unscoped lookup, return `403 Forbidden`, or include ownership-specific details.

Apply the rule to direct get, PUT, PATCH, and delete routes; the parent collection in the nested bookmarks route; bookmark filtering by `collectionId`; and non-null bookmark `collectionId` values supplied for create, PUT, or PATCH. An owned collection containing no bookmarks returns a successful empty list, while a missing or other-owner collection returns the generic 404.

The shared JSON error-body shape is defined in ADR-012 and must be identical for missing and other-owner cases.

### Rationale

Using one owner-scoped query path and one response prevents the API contract from becoming a resource-enumeration oracle. It also makes owner scoping the normal data-access pattern rather than a check performed after loading another user's row.

### Consequences and trade-offs

- A caller cannot distinguish a mistyped identifier from an identifier owned by someone else.
- Ownership mismatch does not use `403 Forbidden`.
- Logs and client-facing errors must not add details that defeat the uniform response policy.
- Tests must compare both status and body for missing and other-owner identifiers across every applicable path.

## ADR-012: Wrap success and error responses in consistent envelopes

- Status: Accepted
- Date: 2026-08-05

### Context

The frontend benefits from predictable response shapes across resources and operations. Including status and message fields in successful bodies duplicates some HTTP information but provides a visually consistent API contract. A body is not permitted with `204 No Content`, so requiring a delete envelope also requires a different successful delete status.

### Decision

Every successful response contains `statusCode`, `message`, and `data`. The body status is derived from and must equal the actual HTTP status. GET, PUT, PATCH, and DELETE use `200 OK`; POST uses `201 Created`. Single-resource operations place the resource in `data`, list operations place an array in `data`, and DELETE places null in `data`. DELETE does not use 204.

Every error response contains `statusCode`, `code`, `message`, and `details`, with `details` always an array. Validation failures use 400 / `VALIDATION_ERROR` / `Request validation failed`; authentication failures use 401 / `UNAUTHORIZED` / `Unauthorized`; missing and other-owner resources use 404 / `NOT_FOUND` / `Resource not found`; unexpected failures use 500 / `INTERNAL_SERVER_ERROR` / `Internal server error`.

Validation details may name fields and constraints but never echo submitted values. Authentication, privacy, and internal errors expose no sensitive or implementation details. Success messages are descriptive only and must not drive frontend control flow. List pagination metadata is defined in ADR-014.

### Rationale

The envelope gives frontend calls a uniform place to read data and offers human-readable operation context. Keeping the actual HTTP status authoritative and deriving the body value prevents the duplicated status from drifting. A stable machine-readable error `code` avoids coupling frontend behavior to messages.

### Consequences and trade-offs

- Response bodies are slightly larger and less idiomatic than returning bare resources or arrays.
- DELETE returns 200 with a JSON body instead of the common 204 response.
- Middleware or interceptors must prevent the actual and body status values from diverging.
- Frontend logic uses HTTP status and error `code`, not success or error message text.
- Privacy tests must compare the complete 404 body for missing and other-owner cases.
- Contract tests must cover response shapes, status equality, and redaction of sensitive values.

## ADR-013: Use minimal owner-scoped list filters

- Status: Accepted
- Date: 2026-08-05

### Context

The assignment requires filtering for collections and bookmarks and specifically requires the frontend to filter bookmarks by collection. It does not define collection-filter parameters or how to select uncategorized bookmarks. Full-text search is optional rather than core scope.

### Decision

Support `GET /collections?name=<text>` as a case-insensitive substring match. Trim the value and require 1–100 characters. Omitting `name` returns all collections within the authenticated owner's scope.

Support `GET /bookmarks?collectionId=<uuid>` for one owned collection and `GET /bookmarks?uncategorized=true` for bookmarks whose `collectionId` is null. When `uncategorized` is present, the only supported value is the literal `true`. Omitting both parameters returns all of the owner's categorized and uncategorized bookmarks. Reject a request that combines `collectionId` and `uncategorized=true`.

A malformed collection UUID receives `400 VALIDATION_ERROR`. A syntactically valid collection ID that is absent or owned by another person receives the uniform `404 NOT_FOUND` response from ADR-011 and ADR-012. An owned collection containing no bookmarks succeeds with an empty list.

Do not add URL search, title search, full-text search, owner filters, or multiple collection IDs to the core contract. Ordering and pagination are defined in ADR-014.

### Rationale

These parameters satisfy the required collection and bookmark filtering with a small, explicit contract. A separate `uncategorized=true` flag preserves UUID validation for `collectionId` and avoids magic values such as the strings `null` or `uncategorized`. Owner scoping before filtering and uniform inaccessible-collection behavior preserve the privacy boundary.

### Consequences and trade-offs

- Collection-name matching is partial and case-insensitive rather than exact.
- Bookmark filters select one collection, uncategorized bookmarks, or all bookmarks; multi-collection filtering is unsupported.
- The literal `uncategorized=true` is supported; other values are invalid rather than defining additional category states.
- Full-text and field-specific bookmark searching remain outside the core submission.
- Tests must cover filter validation, empty results, nested-route equivalence, and two-user isolation.

## ADR-014: Bound list queries with offset pagination

- Status: Accepted
- Date: 2026-08-06

### Context

The assignment does not require pagination, but unbounded list responses can increase database work, backend memory use, response size, and frontend rendering cost as a user's bookmark data grows. Cursor pagination scales better at very large offsets, while page-based offset pagination is simpler for the required frontend and expected personal-bookmark workload.

### Decision

Apply offset pagination to the collection list, bookmark list, and nested collection-bookmark list. Accept `page` as an integer of at least 1 with a default of 1. Accept `pageSize` as an integer from 1 through 100 with a default of 20. Invalid values receive `400 VALIDATION_ERROR`.

Apply authenticated-owner scope and filters before counting and selecting results. Order lists by `createdAt DESC`, then `id DESC`. Return list metadata `{ page, pageSize, total, totalPages }`, where the total uses the same owner and filters and total pages is `ceil(total / pageSize)`, or 0 for no results.

A page beyond the available results succeeds with an empty data array and retains the requested page plus actual totals. Inaccessible parent or filter collections still receive the privacy-preserving 404 before pagination is applied.

Add composite indexes on collection `(ownerId, createdAt DESC, id DESC)`, bookmark `(ownerId, createdAt DESC, id DESC)`, and bookmark `(ownerId, collectionId, createdAt DESC, id DESC)`. Do not add cursor pagination, full-text indexes, or trigram indexes to the core submission.

### Rationale

A default and maximum page size bound normal list work without adding the cursor lifecycle and frontend state needed for cursor pagination. The timestamp-plus-UUID ordering produces stable tie-breaking, and owner-scoped totals prevent metadata from leaking other users' record counts.

### Consequences and trade-offs

- List requests require both a count and a page query.
- Large valid offsets become slower as page numbers grow; cursor pagination would be reconsidered if measurements show this matters.
- Concurrent inserts or deletes can shift records between offset-based pages.
- Every list response includes pagination metadata, including empty lists.
- Tests must cover parameter validation, stable ordering, page boundaries, filter interaction, and owner-isolated totals.

## ADR-015: Expose collection bookmarks through a read-only nested route

- Status: Accepted
- Date: 2026-08-06

### Context

The assignment explicitly requires `GET /collections/:id/bookmarks`. The API already supports the equivalent bookmark `collectionId` filter, so the nested route needs clear ownership, validation, pagination, and mutation-boundary semantics without duplicating the entire bookmark API below collections.

### Decision

Implement `GET /collections/:id/bookmarks?page=<page>&pageSize=<pageSize>`. Validate the collection ID as a UUID and resolve the parent using both ID and authenticated `ownerId`. A malformed UUID receives `400 VALIDATION_ERROR`; a missing or other-owner collection receives the identical privacy-preserving 404; and an owned empty collection returns a successful paginated empty list.

Count and query bookmarks using both authenticated `ownerId` and parent `collectionId`, with the ordering and pagination from ADR-014. The nested endpoint accepts only `page` and `pageSize`; reject `collectionId`, `uncategorized`, collection-name filters, and unsupported query parameters.

For the same collection and pagination values, the nested route and `GET /bookmarks?collectionId=<id>` return equivalent bookmark data and metadata. Implement no nested bookmark mutations; create, PUT, PATCH, and DELETE remain under `/bookmarks`.

Nesting is relational navigation rather than embedded storage. After collection deletion, the nested route returns 404 while the preserved bookmarks are available through the uncategorized filter.

### Rationale

The route directly satisfies the assignment and gives the collection page a clear read path. Keeping mutations canonical under `/bookmarks` avoids duplicate contracts, while owner scoping both the parent and bookmark queries provides defense in depth against cross-owner data exposure.

### Consequences and trade-offs

- Two GET forms expose the same collection-specific bookmark list and must remain behaviorally consistent.
- The route cannot represent uncategorized bookmarks because it requires an existing parent collection.
- Clients cannot mutate bookmarks through the nested path.
- Tests must cover parent validation and privacy, empty and populated pages, filter-route equivalence, unsupported parameters, and post-deletion behavior.

## ADR-016: Use Vitest for frontend tests and Jest for backend tests

- Status: Accepted, with remaining test design pending
- Date: 2026-08-06

### Context

The assignment requires automated tests but does not prescribe test frameworks. The React/Vite frontend and NestJS backend need test runners that fit their respective toolchains, while the test layers, supporting libraries, database lifecycle, end-to-end approach, and coverage policy have not yet been selected.

### Decision

Use Vitest as the frontend test runner. Use Jest with Nest testing utilities (`@nestjs/testing`) as the backend test runner. The remaining test architecture is selected in ADR-019.

### Rationale

Vitest integrates naturally with the Vite-based frontend, while Jest and Nest's testing utilities provide the conventional Nest application and dependency-injection test harness. Selecting one runner per service avoids overlapping test-runner configuration.

### Consequences and trade-offs

- Frontend and backend tests use different runner APIs and configuration files.
- Shared test concepts should not depend on runner-specific globals where avoidable.
- This decision alone does not prove the required authentication, privacy, persistence, frontend, or end-to-end behavior; the remaining test design must define those layers.

## ADR-017: Bound initial `/userinfo` enrichment to 1500 milliseconds

- Status: Accepted
- Date: 2026-08-07

### Context

Initial local-user provisioning may enrich nullable display fields from Auth0
`/userinfo`, but a profile service must not hold an authenticated API request
open indefinitely. The assignment requires one short timeout and says that a
timeout or profile failure must not reject the authenticated request.

### Decision

Use a 1500 ms `AbortController` timeout for the one `/userinfo` request made
when a verified Auth0 subject is first provisioned. A non-2xx response, timeout,
network failure, malformed JSON, or unavailable profile values leaves the
nullable `email` and `name` fields empty and the request continues. Existing
local users do not call `/userinfo` again.

### Rationale and trade-offs

1500 ms is short enough to bound login-path latency while allowing a normal
same-region profile request. It can omit optional profile data during transient
latency, which is acceptable because profile values are display-only and the
verified `(iss, sub)` identity remains authoritative.

## ADR-018: Use Auth0 React SDK for the browser OIDC client

- Status: Accepted
- Date: 2026-08-07

### Context

The frontend needs Authorization Code flow with PKCE (`S256`), the supplied
Auth0 tenant, the assignment client ID, callback URL
`http://localhost:3000/callback`, logout URL `http://localhost:3000`, the API
audience, and `openid profile email` scopes. The assignment leaves the React
OIDC library open.

### Decision

Use `@auth0/auth0-react`. Its provider owns the browser authorization-code/
PKCE redirect state, token cache, login, logout, and access-token retrieval.
The API client requests a token for the configured API audience and calls only
the backend with that access token; it never sends an ID token as API
authorization. Configuration is supplied through Vite environment variables,
not source-controlled credentials.

The latest published `react-router-dom` package available in the configured
npm registry during implementation is 7.18.2; no 8.x release or prerelease is
published there. The frontend therefore uses that latest available major and
records the assignment's 8-or-newer router requirement as an external
dependency TODO rather than inventing an unpublished package version.
MUI is pinned to the available 9.x line.

### Trade-offs

The Auth0 SDK reduces protocol and token-cache code in the browser, but it is a
runtime dependency and still requires a real tenant configuration for an
end-to-end sign-in. The router version discrepancy is documented honestly and
must be revisited if the assignment environment provides React Router 8.

### Evidence

- [Auth0 React SDK](https://dev.auth0.com/docs/libraries/auth0-react) — documents Authorization Code with PKCE and audience/scope access-token retrieval.
- [Auth0 PKCE authorize endpoint](https://auth0.com/docs/api/authentication/authorization-code-flow-with-pkce/authorize-with-pkce) — documents `code`, `S256`, and API audience usage.

## ADR-019: Select the verification layers and lifecycle

- Status: Accepted
- Date: 2026-08-07

### Decision

Use these runnable layers:

1. Backend Jest unit tests for DTO rules, pagination, response/error mapping,
   JWT validation, user provisioning, owner-scoped service branches, and
   atomic deletion calls.
2. Backend Nest testing utilities plus Supertest for HTTP contract tests. The
   application uses a controlled Prisma test double for fast contract/privacy
   cases, while dedicated AuthService tests exercise the real `jose` validation
   path with generated RSA keys and a controlled JWKS server. This split and
   the test doubles are disclosed in the test files and README.
3. PostgreSQL integration tests are run against the Docker Compose database
   after `prisma migrate reset` and `prisma db seed`; they are opt-in when
   `DATABASE_URL` and a reachable database are present so the default unit
   suite remains reproducible without Docker.
4. Frontend Vitest tests use jsdom and React Testing Library for authenticated
   loading, collection/bookmark CRUD actions, filtering, and fallback profile
   labels. Browser-level Auth0 E2E is an environment-only smoke test and is not
   required for the default test command because it needs supplied credentials.

No arbitrary global coverage percentage is claimed. The required endpoint,
authentication, privacy, validation, pagination, and frontend operation matrix
is the acceptance threshold, with coverage reports available through the
backend and frontend test commands.

### Rationale and trade-offs

The split keeps local verification fast while still exercising the real token
validator and providing a documented SQL lifecycle for persistence tests. It
does not claim live Auth0 sign-in in an environment that lacks the tenant client
configuration or test credentials.

## ADR-021: Handle expired or rejected API sessions in the frontend

- Status: Accepted
- Date: 2026-08-07

### Context

The backend correctly returns the generic `401 UNAUTHORIZED` envelope when an
access token is missing, expired, invalid, or fails the Auth0 validation rules.
Previously, the frontend displayed the request error but left the Auth0
session state unchanged, so the user could remain on an authenticated page
after the API rejected the token.

### Decision

When `apiRequest` receives HTTP 401, `useApiRequest` invokes Auth0 logout once
for the mounted request hook and returns to `http://localhost:3000`. The
application then observes `isAuthenticated === false` and renders the normal
sign-in page. The backend remains strict; the frontend does not retry with an
ID token or suppress the API error.

Backend Auth0 configuration is kept separate from frontend Vite configuration
and must be present in the backend runtime environment. `backend/.env.example`
is the source template; `frontend/.env` is never loaded by NestJS.

### Evidence

- `frontend/src/api/client.auth.spec.tsx` verifies one logout call and the
  configured local return URL after a 401.
- A controlled backend repro confirms an empty `AUTH0_CLIENT_ID` produces
  `UnauthorizedException:401` before token verification.

## ADR-022: Use shared bookmark dialogs and lazy collection previews

- Status: Accepted
- Date: 2026-08-07

### Context

The original frontend created bookmarks in a large inline form, exposed no
bookmark edit flow, and required navigation to a collection detail page before
its bookmarks were visible. The requested refresh needed a smaller MUI layout
without adding filtering or resource behavior outside the assignment.

### Decision

Use one reusable bookmark dialog across list and detail views. Creation sends
`POST /bookmarks`; editing submits the complete writable representation with
`PUT /bookmarks/:id`. Collection rows use single-open MUI accordions and load
bookmarks only when expanded through the existing nested endpoint, defaulting
to five items. Loaded nested pages are cached until a related create, edit, or
delete invalidates them. Every visible list offers page sizes 5, 10, 20, 50,
and 100 and resets to page 1 when the selection changes. The bookmark list
continues to support only All, Uncategorized, or one owned collection, and
its MUI dropdown searches those collection options locally. Collection
selectors follow all paginated collection results in 100-item API pages.

### Rationale and trade-offs

The shared dialog keeps validation and null normalization consistent while the
lazy accordion avoids requesting bookmark pages the user has not opened. A
five-item accordion default keeps the collection list compact, while users can
choose a larger page and full lists retain a 20-item default. Cache invalidation
adds frontend state handling, so tests explicitly cover moves between
collections, deletion, nested pagination, page-size changes, and out-of-range
pages.

### Evidence

- Frontend Vitest and React Testing Library suites cover the dialog and all
  four resource pages, including page-size changes: 36 tests across nine test
  files.
- Frontend typechecking and the Vite production build pass. The build retains
  the existing non-blocking warning for a JavaScript chunk larger than 500 kB.

## ADR-023: Persist the Auth0 SDK cache across page reloads

- Status: Accepted
- Date: 2026-08-08

### Context

The frontend configured the Auth0 React SDK with an in-memory cache. A full-page
reload therefore discarded the cached access token and depended on silent Auth0
session recovery to reconstruct the signed-in state. That recovery depends on
browser cookie behavior. The candidate reported that the current browser flow
appeared signed out after refreshing the application.

The installed Auth0 SPA SDK provides `memory` and `localstorage` as built-in
cache locations. Using `sessionStorage` would require a custom cache
implementation, adding authentication code that the SDK would otherwise own.

### Decision

Configure `Auth0Provider` with the SDK-managed `localstorage` cache. Do not read,
write, or interpret token values in application code. This preserves the SDK's
cache-key, expiry, and token-selection behavior while allowing the authenticated
state to survive a page reload.

Do not enable refresh tokens as part of this change. Refresh-token rotation must
first be confirmed as enabled for the supplied Auth0 SPA client and verified
against a real audience-bound token.

### Rationale and trade-offs

Local storage provides reliable reload and cross-tab persistence without a
custom cache. Unlike memory storage, it is readable by JavaScript on the same
origin, so an XSS defect could expose cached bearer credentials. The frontend
must therefore avoid unsafe HTML injection and keep its dependency and content
security posture under review. This is an explicit usability-versus-exposure
trade-off rather than a claim that local storage is intrinsically secure.

### Evidence

- `frontend/src/auth/config.spec.ts` locks the selected SDK cache location to
  `localstorage`.
- The provider consumes that exported setting directly; application code does
  not manually store bearer tokens.
- A live reload through the supplied Auth0 tenant remains an environment smoke
  test and is not claimed by the deterministic Vitest configuration test.
